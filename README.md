# API-автотесты банковского сервиса

Проект автоматизации тестирования REST API. Фреймворк написан с нуля на
Python + pytest + requests + pydantic, с разделением на слои ответственности.
Результат каждой операции проверяется дважды: по ответу API и по состоянию
базы данных.

---

## Тестируемое приложение

Банковское REST API, запускается локально в Docker.

| | |
|---|---|
| Base URL | `http://localhost:4111/api` |
| Swagger UI | `http://localhost:4111/api/swagger` |
| Контракт | `http://localhost:4111/api/swagger.json` |

Покрытые ручки: аутентификация, создание пользователей, создание счетов,
пополнение, переводы, выдача и погашение кредитов.

---

## Стек

- **Python 3** — язык
- **pytest** — раннер, маркеры, параметризация, фикстуры
- **requests** — HTTP-клиент
- **pydantic** — типизированные модели запросов и ответов, валидация тел
- **SQLAlchemy** — доступ к БД тестируемого приложения (PostgreSQL)
- **Allure** — отчётность, шаги и вложения на уровне реквестеров

### Границы слоёв

Основной принцип: **каждый слой отвечает ровно на один вопрос**.

| Слой | Отвечает на вопрос | Не знает о |
|---|---|---|
| `RequestSpecs` | Кто стучится: админ, пользователь, аноним | Какую ручку дёргают |
| `ResponseSpecs` | Тот ли статус-код пришёл | Что лежит в теле |
| `CrudRequester` | На какой URL идти и во что превращать тело | Что означает результат |
| `steps` | Какое бизнес-действие выполняется | Как устроен HTTP |
| `models` | Какие поля и типы допустимы | Откуда взялись данные |
| `db/crud` | Что записано в базе | Как данные туда попали |
| `tests` | Что означает результат операции | Всё вышеперечисленное |

Тест не собирает запросы руками — он вызывает шаг:

```python
api_manager.user_steps.transfer_account(user, from_account, to_account, 3000)
```

### Два реквестера вместо ветвления

Реквестер не выясняет по статус-коду, успех перед ним или ошибка — это решает
тест, и говорит об этом **выбором шага**:

```python
# позитивный кейс — ValidateCrudRequester, ответ разбирается моделью ручки
api_manager.user_steps.transfer_account(user, from_account, to_account, 3000)

# негативный кейс — ErrorCrudRequester, ответ разбирается моделью ошибки
response = api_manager.user_steps.transfer_account_invalid(user, from_account, to_account, 0)
assert response.error == "Amount must be greater than 0\nAmount must be between 500 and 10000"
```

Каждый метод возвращает ровно один тип, поэтому аннотация возврата честная,
а в тестах нет ни разбора сырого JSON, ни ветвлений. Тело ошибки описано
единой моделью `ErrorResponse` — формат ответа об ошибке одинаков на всех ручках.

## Проверка состояния через БД

Ответ API говорит только то, что сервис **сообщил о себе**. Проверка через
базу отвечает на вопрос, что он на самом деле записал. Показательный пример —
погашение кредита: в ответе приходят лишь `creditId` и `amountDeposited`,
а списались ли деньги и закрылся ли долг, знает только база.

Фикстура `db_session` открывает соединение и транзакцию, а после теста делает
`rollback` — тест ничего не оставляет за собой на своей стороне. Созданные
через API пользователи удаляются отдельно, через реестр `created_obj`.

Структура каждого теста одинакова:

```
предусловие → одно действие → проверка ответа → проверка состояния БД
```

Предусловие проверяет, что подготовка сработала: тест падает до основного
действия, а не после него с непонятной причиной. Негативные кейсы отдельно
доказывают, что **ничего не изменилось**: балансы прежние, лишних транзакций
и кредитов в базе нет.

Отдельный нюанс — кэш сессии SQLAlchemy. В рамках одной `Session` строка
таблицы соответствует одному Python-объекту, и повторный запрос вернёт тот же
объект со старыми полями. Данные меняются снаружи, по HTTP, поэтому перед
повторным чтением вызывается `db_session.expire_all()`.

### Секреты

В коде нет ни одного пароля. Учётные данные и строка подключения к базе
читаются из переменных окружения или из локального `.env`, который не
коммитится. В репозиторий уезжает только `.env.example` с пустыми значениями.

## Запуск

**Требуется:** Python 3.10+, поднятый локально бэкенд на `http://localhost:4111`
и доступ к его базе PostgreSQL.

```bash
# 1. зависимости
python -m venv .venv
.venv/Scripts/activate        # Windows
pip install -r requirements.txt

# 2. учётные данные и подключение к базе
cp .env.example .env          # заполнить ADMIN_USERNAME / ADMIN_PASSWORD / dataBaseUrl

# 3. прогон
pytest src/main/api/tests -q                            # все тесты
pytest -m api                                           # только помеченные маркером api
pytest src/main/api/tests/t07_credit_repay_test.py -q   # один файл
```

Отчёт Allure собирается в `allure-results` при каждом прогоне:

```bash
allure serve allure-results
```

## Найденные дефекты

Расхождения реализации с опубликованным контрактом OpenAPI, найденные при
написании негативных кейсов.

### 1. `/account/deposit` — недокументированные границы суммы

```
amount=999      → 400 "Amount must be between 1000 and 9000"
amount=1000001  → 400 "Amount must be between 1000 and 9000"
```

Текста «Amount must be between 1000 and 9000» в контракте нет.
Задокументированный «Amount cannot exceed 1,000,000» не приходит никогда.

### 2. `/credit/request` — не то имя поля в ответе 201

```
по контракту: {"accountId": 1,   "amount": 5000, "termMonths": 12, ...}
фактически:   {"id":        119, "amount": 5000, "termMonths": 12, ...}
```

Клиент, написанный строго по контракту, упадёт на разборе ответа.

### 3. `/credit/request` — не тот код и текст на превышение лимита

```
по контракту: 422 "Credit amount cannot exceed 15000"
фактически:   400 "Amount must be between 5000 and 15000"
```

Код 422 не приходит ни при каких значениях. Фактического текста в контракте нет.

### 4. `/credit/repay` — `accountId` фактически обязателен

Контракт объявляет `required: [creditId, amount]`, поле `accountId`
опциональное. Проверено экспериментом — без него запрос не проходит:

```
без accountId    → 400 {"error": "This value should be of type int."}
amount="сто"     → 400 {"error": "This value should be of type float."}
```

Сообщения не называют проблемное поле. Три задокументированных текста
(`Credit ID is required`, `Amount is required`, `Invalid request body`)
недостижимы.

### 5. `/account/transfer` — недокументированные границы суммы

```
→ 400 "Amount must be between 500 and 10000"
```

Текста в контракте нет. Аналогично дефекту №1.

### Закономерность

Собственная бизнес-валидация приложения контракту соответствует дословно.
Проверки **типа и наличия** поля до неё не доходят — их перехватывает валидатор
фреймворка и возвращает служебный текст, которого в контракте нет. Отсюда же
недостижимость части задокументированных сообщений об ошибках.

## Наблюдение по модели данных

Долг по кредиту хранится в таблице `credit` со знаком минус: сразу после
выдачи `amount = 5000`, `balance = -5000`. Погашение прибавляет к остатку,
при полном погашении `balance` становится `0`. Поведение согласованное,
дефектом не является — зафиксировано, чтобы знак не выглядел ошибкой при
чтении тестов.
